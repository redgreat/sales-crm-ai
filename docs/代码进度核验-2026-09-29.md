## 3. P3：核心补参已有，不能整体完成

已存在：`graphs/nodes.py`、`interrupts.py` 的结构化补参与中断；会话/消息持久化、close、Run pending/resume 与 owner 校验；问答图 `qa.py` 和 executor 将历史标作 `[H]`，不纳入合法事实引用。本次纯图测试通过。

仍有以下交付缺口：

1. `persistence/conversations.py::list_messages` 是 `ORDER BY seq LIMIT 100`，取最早消息，不是最近完整轮次窗口；executor 直接使用这些历史。尚无可验证的摘要/窗口保留策略。
2. 历史不允许作为 citation，并不等于历史已获当前授权。没有看到逐轮对历史正文、摘要及 checkpoint 重新校验 CRM 来源权限的闭环；知识新检索过滤不能替代历史撤权。
3. close 接口已存在，但清空、过期清理、关闭后从所有 Run 入口阻止继续使用、切换对象后旧候选/会话失效仍需整体测试。
4. `/conversations/{id}/messages` 仍固定调用 `communication.extract`；默认幂等键按会话/用户生成，不区分新一轮，重复追加消息/并发恢复需验证。对象问答走 `/runs` + conversation_id，不能把两入口视为完全一致。
5. 该 messages 自动恢复分支未接受前端 state_version；独立 `/runs/{id}/resume` 的版本校验不能证明所有恢复入口都安全。需统一版本与消息幂等契约。
6. `test_object_qa_conversation_binding` 验证对象绑定与单次回答消息，不足以证明长会话完整轮次、旧事实撤权或旧状态跨版本恢复。

结论：可标“补参底座与部分问答代码已实现”，窗口/生命周期/撤权/多入口一致性仍保留未完成。

## 4. P4：由未开始改为进行中，正式闭环尚未验收

已定位到 CRM 工作区：

- `salescrm-api/.../controller/AiIntegrationController.java`：创建/查询/pending/resume、导入、列表、confirm/retry/ignore、客户事实。
- `salescrm-service-impl/.../ai/AiRunClient.java`、`impl/AiIntegrationServiceImpl.java`：HMAC 出站、导入、匹配、本人候选查询、先活动后任务、原业务键查询与重试。
- `salescrm-web/.../filter/AiServiceSignatureFilter.java`：签名/时间窗/nonce 校验。
- `SalesActivity`、`SalesTask`、`AiCandidate` 实体/Mapper 与 `V010__ai_agent_candidates.sql`，以及 JDBC 验收测试文件。

不能整体勾选完成的原因：

1. **迁移版本冲突**：同目录已有 `V010__processing_job_lease.sql`，新增 `V010__ai_agent_candidates.sql` 不能作为可直接发布迁移；需核实各环境历史后分配新版本，不盲改已执行文件。
2. **对象与指派授权不完整**：匹配不带客户范围；`applyOverrides` 接受 customer_id 后直接标 MATCHED，`readyForWrite` 仅检查字段。需走正式访问策略、对象状态和员工/组织指派规则，不能只凭本人候选或 R1/R2 标签。
3. **默认业务值不等于人工补齐**：有 override 但未给负责人时会默认本人；活动时间缺失默认当前时间。应明确展示并让用户确认，不能用“谁发起谁确认”推导负责人已确认。
4. **未复用完整正式 Service**：当前在集成服务直接用 Mapper 插入活动/任务；正式对象与候选写入回执分开提交，未看到同事务确认快照/正式审计完整链路。稳定业务键提供部分恢复基础，但不等于全链路一致性完成。
5. **提交与确认契约不足**：createRun 每次生成随机请求键，不能防移动端重复点击/弱网重投；confirmRun 的 items 是 override 而不是明确勾选集合，方法仍遍历整批候选，缺候选版本/来源版本/冻结最终值的强校验。
6. **测试不能代替业务路径**：Java `candidateVersionChangeDetected` 只检查改过的 JSON；`sourceRevocationHandled` 直接把候选改 INVALID；`activityFailureStopsTaskCreation` 预置状态后查询。这些不证明 Controller/Service 真正阻止旧版本、撤权或失败后写入。
7. Python `test_crm_integration.py` 的部分“全链路”断言接受全部写入失败；必须新增强断言：真实合法测试数据至少成功创建活动和任务，并查回正式对象，重复/超时仍返回同一 ID。

建议顺序：先修迁移和事实契约 → 客户/员工权限与确认选择/版本 → 正式 Service、事务/审计及对账 → 测试环境真实写入与弱网重放。此报告只登记缺口，不修改代码。
