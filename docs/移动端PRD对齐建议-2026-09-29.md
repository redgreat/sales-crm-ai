# 移动端 PRD 对齐建议（评审稿）

> 2026-09-29｜移动端仍在更新，本报告是当前文件快照，不是批准变更。只修改 AI 项目文档，不改移动端或后端 PRD。

## 1. 依据与总体评价

移动端来源：[README](../../sales-crm-api-service/docs/瑞赢1.0-移动端原型/README.md)、[DEV_SPEC](../../sales-crm-api-service/docs/瑞赢1.0-移动端原型/assets/dev-spec.js) 及相关 pages HTML。README 标为 V2.1，生成时间 2026-09-16；这是包内标识，不代表用户本次更新时间。后端依据：[05 AI](../../sales-crm-api-service/docs/V0.1.0/瑞赢首个销售闭环/prd/05-Agent候选与人工确认.md)、[04 任务/活动/日程/日报](../../sales-crm-api-service/docs/V0.1.0/瑞赢首个销售闭环/prd/04-任务销售活动日程与日报.md)、[08 知识与治理](../../sales-crm-api-service/docs/V0.1.0/瑞赢首个销售闭环/prd/08-PC基础平台与集成治理.md)。

优点：28 个稳定 page-id、业务页内就近入口、上传归属确认、纪要与任务分开、统一助手及知识服务端过滤，适合销售移动操作。缺点不是“页面少”，而是旧业务口径仍混在状态、接口和按钮里：若按页面直接写代码，会做出与正式 CRM 不同的任务/候选/通知体系。当前适合作交互素材，尚不足以冻结接口和上线验收。

本轮评价为需求/状态/接口一致性检查，未做浏览器视觉、可访问性或真实移动端性能测试。不按图中示例数据认定产品功能已实现。

优先级：**阻断**必须在真实写入前确定；**高**在相关能力上线前补齐；**待确认**为新范围，不自动进入一期。后端 Coze 必选技术条款已被 Python 决策替代，但其业务权限/确认红线继续适用。移动端文件较新或正在修改，也不能自动覆盖已批准业务规则。

## 2. 阻断差异及可直接采用的修订方向

### M-01 候选状态与 24 小时过期（阻断）

来源：DEV_SPEC M03、M26；模型 `expireAt(24h)`、草稿与正式任务同表、状态“已调整/已驳回”，驳回理由必填并回流模型。后端 05 §9～10 为待确认/已确认/已忽略/已失效；修改属于确认方式，久未处理进入历史待处理而非失效。

建议：改为“AI 待确认”，独立展示候选状态、确认方式、写入状态；去掉固定 24h 自动失效和必填驳回理由。允许候选持久化用于恢复/审计，不计入正式事实。用户忽略仅留审计，不自动上传训练或回流外部模型。会话 TTL 不能改变候选业务状态。

### M-02 批量确认与追踪任务（阻断）

来源：M03 通用 batch-confirm、M06/M07/M25 自动生成负责人追踪任务及协作者各自待办；M25 HTML 按钮也写“生成待办与追踪任务”。后端 05 §8～9 仅同会议来源批量确认、逐项校验与部分成功；04 正式任务模型不应被原型派生为另一套追踪任务。

建议：仅同会议来源勾选批量；确认者为提炼发起人，责任人可不同。确认结果逐项列正式 ID、未执行/失败原因和原键重试；先活动后任务，不整批回滚、不新增追踪任务。多人协作按正式任务关系实现，不能把“协作人”隐式变成多个正式任务。

### M-03 助手创建新业务对象（阻断/待确认扩范围）

来源：M20 `/assistant/draft/{visit|customer|lead|opportunity|contact}`、“先匹配再补增”“确认前不落库”。后端 05 §6～7 不允许无匹配自动建客户/联系人/线索/商机，核心候选为销售活动/任务，不能直接写正式拜访。

建议：一期快捷入口限定沟通整理、摘要/问答、知识、会前准备和日报等已批准能力；新增客户/联系人等跳正式手工建档页。若产品坚持对话建档，单独新增变更单、权限/必填/查重/证据和验收，不借“本人确认”默认扩范围。“确认前不落库”改为“确认前不写正式业务表”，来源/Run/候选必须可持久恢复。

### M-04 工作手机录音与自动采集（阻断/待确认扩范围）

来源：M10 自动采集、M13 签到触发工作手机后台录音、M14 SDK 启停、M24 开会录音链路；后端 05 §2.3/18 明确本期不进入工作手机自动采集。

建议：一期使用用户主动录音/授权上传/文字粘贴，ASR 作为增强输入逐项 POC；显示录音授权、处理中、失败转文字。会议结束后提供主动“整理纪要”，不能因结束事件默认启动未批准的自动 AI 流程。实时会议转写/后台录音单独评审，不借 H5 接口伪装成已支持。

### M-05 人工确认身份与正式任务状态（阻断）

来源：M04/M05/M07 简化的“待办→提交→确认”与追踪人双确认，M25 会议创建人闭环。后端 04 §2 区分来源、接收和验收快照；05 §8 谁提炼谁确认。

建议：分别呈现“AI 候选确认”“正式任务接收”“正式任务验收”，三者不是一次动作。给自己建任务按正式规则进入进行中，指派他人进入待接收；验收人按业务快照确定，不默认会议主持人/追踪人。普通主管统计权限不赋予代确认权。

## 3. 高优先级交互与范围差异

### M-06 助手只缓存前端会话（高）

M19 `assistant_session` 前端缓存、不落业务库、收起保留，可作为 UI 状态但不足以支持持久记忆。需求规定服务器会话与 checkpoint。建议每次打开用 conversationId/runId 恢复，收起不取消、刷新不丢失；明确新会话/结束/过期、对象切换提示、来源撤权。UI 不展示内部 thread_id 作为权限凭证。

### M-07 缺少证据与失败写入独立视图（高）

M03/M15/M25 主要突出草稿到生效，未完整约定逐字段证据/原建议与人工最终值、已确认但写入失败、部分成功及原键重试。建议增加当前/历史待处理/写入失败分组，显示来源版本、缺项和影响；普通跨来源不提供全选确认。离页与弱网重复提交返回原 Run/正式对象，不再生成新结果。

### M-08 自动推送和消息偏好（高）

M02/M27 有 L1～L4、时间窗合并、个人企微/免打扰设置，M03 普通草稿提醒；后端 04 §7/§8 排除复杂消息等级、时间窗合并、个人偏好，普通候选/AI 建议默认不推企微；05 §4 三项预生成不主动推送。

建议：保留 deep link 和服务端发起方向，改为系统白名单及事件版本幂等；移除一期个人通知配置。**日报未提交提醒是正式业务白名单事件，可保留**，不能把它与“AI 日报生成完成推送”混为一谈；正式拜访提醒遵循企微日程规则，避免重复推送。

### M-09 日报模型不完整（高）

M16 单 body/status、固定 18:30、已发送不可改。后端 04 §5/05 §11 为首次底稿、工作草稿、提交快照，时间可配置，已编辑刷新须提示。

建议：区分“生成/刷新底稿”和“提交日报”；展示截至时间及新事实提示，保留人工编辑，只有正式事实进入正文。无事实可手填非空说明；“发送”若等同提交需写明，不额外扩展自主对外发送。

### M-10 知识分享和权限（高/待确认）

M17 业务线×角色，M18 外部转发 JS-SDK、allowExternal、水印及专门日志；后端 08 §12 支持全员/角色/业务线发布范围，有权查看即可下载，只支持复制链接并打开重鉴权。

建议：明确角色与业务线组合是交集还是并集，不由前端自行计算；一期改成复制受控链接/有权下载，外部转发及水印不当成安全授权。只检索已发布当前版本；旧回答不改写历史事实，但撤权后应限制其内容展示和再次送模型，而不只是隐藏引用。

### M-11 日程与拜访边界（高，主要属于 CRM）

M08 独立日程加投影方向正确，可保留；但 M21/M22 “计划中/进行中/已结束”与后端 04 §4 独立日程“有效/已取消/已删除”不同，展示时间态不能成为新业务主状态。M13/M14 的签到、录音、ASR和M15纪要应分离：AI 摘要不能替代签到/签退，也不能绕过正式拜访完成要求。

### M-12 AI 能力入口覆盖不足（高）

当前页面着重任务、拜访、会议和日报，DEV_SPEC 未清楚对应客户/线索/商机摘要、对象/跨对象问答、会前准备、今日任务及主管关注。建议不必为每能力加 TAB，但在 M19 快捷入口/对象详情给出可见条件、当前上下文、能力码、只读标识和源对象返回路径。M01 AI 一句话必须来自确定性底单，不恢复“今日三件事”或模型排序。

## 4. 交付质量改进

README 称 DEV_SPEC 是唯一研发口径，但 notes 渲染版目前缺少完整 note 段，标题也截断；M26 与页内按钮重复存规则，容易漂移。建议以 DEV_SPEC 为源生成 notes/pages 说明，补版本、变更日期、需求编号、审批状态和后端条款映射；每次改状态/接口同时更新 M26 及相关按钮。

每个 AI 入口至少增加：入口 page-id、capability、对象/来源参数、身份获取、Run/会话/候选 ID、状态文案、超时/离页/重试、证据及权限失效、确认者与正式目标、用例编号。原型中的 `/mobile/*`、`/assistant/*` 是拟议路由，不等于现有 CRM API；需要 P4 双端契约映射，不让移动端直接调用 Python 服务密钥接口。

## 5. 提交移动端产品的待确认清单

1. 是否按后端口径取消 24h 自动过期、追踪任务派生与泛化批量确认？
2. M20 对话建档是否明确移出本期，改为手工建档入口？
3. 工作手机自动采集/后台录音是否继续本期排除，M24 改主动上传与主动生成？
4. M27 是否移出一期，只保留白名单消息及 deep link？
5. 知识权限组合和外部转发是否以 08 为准？
6. 确认生产 H5 的实际代码仓库/登录方式；不要把现有 Svelte 联调页或 CRM PC Vue2 页面视为移动端完成。

以上未确认时，AI 团队按现有后端业务红线实现已批准范围，不替产品暗自合并冲突。评审后回填每条 M 编号的决定、版本、负责人及移动端原文改动位置。
